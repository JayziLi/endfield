## 2. 产品概述

Endfield 是一套本地运行的低延迟视觉识别与目标控制工具。它从 OBS 或 UDP 视频源获取画面，使用 ONNX 格式的 YOLO 模型完成目标检测，在指定视野范围内选出目标，并在按住配置的触发键时通过 KMBox Net 发送鼠标移动指令。

产品的主要设计目标是：

- 尽可能降低从接收画面到完成控制指令的本机延迟。
- 支持更换不同类别数量和不同输出排列的 YOLO ONNX 模型。
- 使用图形界面完成日常配置，无需手工修改代码。
- 实时预览按需启用，离开预览页后不占用额外绘制与编码性能。
- 配置保存在可读的 `settings.txt` 中，方便备份和迁移。

当前版本不包含：

- 自动开火或扳机功能。
- Kalman 滤波。
- 完整 PID 中的积分项（I）和微分项（D）。
- OBS 端的 MJPEG 推流插件。
- 云端推理或远程配置服务。
e
当前控制算法为带动态增益和平滑处理的比例控制（P 控制）。

## 3. 使用环境

### 3.1 必需组件

- Windows 11。
- NVIDIA 显卡及可用的 CUDA/TensorRT 运行环境，或使用 CPU 模式。
- ONNX 格式的 YOLO 检测模型。
- OBS 或其他能够输出 UDP JPEG、MPEG-TS/H.264 的画面源。
- KMBox Net 设备；仅查看识别结果时可以关闭 KMBox 控制。

### 3.2 当前验证环境

- 显卡：RTX 4060 Laptop GPU。
- 输入尺寸：`320 x 320`。
- 输入方式：OBS 发送 UDP MJPEG/JPEG 分片。
- 默认监听地址：`0.0.0.0:4455`。
- 推理方式：自动选择 TensorRT FP16、CUDA 或 CPU。

以上内容是已验证环境，不是程序的固定限制。IP、端口、模型和处理尺寸均可配置。

## 4. 系统流程

```text
OBS / UDP 发送端
  -> UDP JPEG 分片、完整 JPEG 或 MPEG-TS/H.264
  -> Endfield 最新帧接收缓冲
  -> JPEG/视频解码与尺寸处理
  -> ONNX Runtime 推理
  -> YOLO 输出自动排列与解码
  -> 分类别 NMS
  -> 按标签、视野范围和距离选择目标
  -> 动态 P 控制与平滑
  -> KMBox Net 相对鼠标移动
```

接收端始终优先处理最新画面。旧帧不会排成长队等待推理，以减少控制结果相对实时画面的滞后。

## 5. 快速开始

1. 启动 OBS 或其他 UDP 发送端，并确认画面正在发送。
2. 双击桌面的 `Endfield` 快捷方式。
3. 在“运行设置”中选择 ONNX 模型和加速方式。
4. 选择画面输入方式，填写本机监听 IP、端口和处理尺寸。
5. 填写 KMBox 地址、端口和 UUID；只测试识别时可取消启用 KMBox。
6. 点击“测试输入”，确认画面输入和 KMBox 连接状态。
7. 在“识别与控制”中设置目标标签、触发键和控制参数。
8. 点击窗口右上角“启动”。
9. 需要查看检测结果时进入“实时预览”；离开该页即停止预览处理。
10. 点击“停止”结束推理与控制。

## 6. 图形界面

### 6.1 顶部状态区

- **启动**：保存当前设置并启动推理流程。
- **停止**：请求推理流程正常退出；超时后程序会结束子进程。
- **状态标记**：显示已就绪、正在启动、等待画面、运行中、正在停止或运行出错。
- **模型测速**：使用固定空白画面测试模型预处理、推理和后处理。
- **管线测速**：使用当前 OBS/UDP 输入和当前模型测试从接收画面到目标选择的完整接收端管线，并保存 JSON 报告。

### 6.2 运行设置

#### 模型

- **ONNX 模型**：选择本地 `.onnx` 文件。
- **加速方式**：支持 TensorRT FP16、CUDA 和 CPU。
- **CUDA Graph**：TensorRT 模式下可启用。程序会固定复用 GPU 输入和输出缓冲，减少每帧提交推理任务的开销；模型不兼容时自动回退到普通 TensorRT 推理。
- **GPU 预处理**：TensorRT 模式下可启用。程序会让 GPU 完成 BGR 转 RGB、张量排列和归一化，原始模型不会被修改；不兼容时自动使用 CPU 预处理。

选择或输入模型路径后，Endfield 会在后台检查模型输出。识别成功时会在运行状态中显示输出尺寸、模型格式和标签范围。

#### 画面输入

支持三种输入：

| 输入方式 | 说明 |
| --- | --- |
| UDP JPEG | 支持完整 JPEG 数据报，也支持从 `FFD8` 到 `FFD9` 的多包 JPEG 分片 |
| UDP MPEG-TS/H.264 | 使用 MPEG-TS 封装的 H.264 UDP 视频流 |
| OBS WebSocket | 通过 OBS WebSocket 请求截图，适合兼容旧流程，不适合追求最低延迟 |

UDP 模式需要设置：

- 监听地址：本机接收网卡的 IP，或使用 `0.0.0.0` 监听全部网卡。
- 端口：发送端的目标端口。
- 处理尺寸：送入模型前使用的画面尺寸。

#### KMBox

- **启用 KMBox 控制**：关闭后仍可接收画面、推理和预览，但不会发送移动指令。
- **设备地址**：KMBox Net 的 IP 地址。
- **端口**：KMBox Net 控制端口。
- **UUID**：设备使用的识别码。

### 6.3 识别与控制

#### 模型输出

- **输出格式**：支持 YOLOv5、YOLOv8 和端到端 NMS 输出。
- **置信度**：过滤低置信度检测框。
- **NMS IoU**：控制重叠框的抑制强度。数值越低，越容易去掉相互重叠的框。
- **运行信息语言**：下方运行状态支持中文或 English。

张量排列不需要用户设置。程序会自动处理 `[1,N,C]` 和 `[1,C,N]`，并兼容动态候选维度、稀疏端到端输出和检测张量不在第一个输出节点的模型。

#### 标签选择

- Endfield 优先读取 ONNX 模型元数据中的 `names`，自动生成 `0` 到 `N-1` 的标签选项。
- 对常见标准输出，可根据输出特征数识别格式和类别数量。
- 无法可靠确定类别数量时，界面回退为 `0–6`，避免沿用上一模型的错误范围。
- 自瞄只会选择当前标签；其他标签不会成为控制目标。
- NMS 按类别分别执行，其他类别的重叠框不会提前压掉当前目标标签。
- 实时预览关闭时，程序只对当前自瞄标签进行 NMS，减少无关后处理；打开预览时恢复全部标签检测，以绘制完整识别结果。

#### 触发方式

支持以下四种触发键：

- 鼠标侧键 1。
- 鼠标侧键 2。
- 鼠标左键。
- 鼠标右键。

只有启用目标控制、KMBox 已连接、检测到所选标签且触发键按下时，程序才会发送移动指令。

#### 动态 P 控制

控制增益根据目标与画面中心的距离动态变化：

```text
Kp = P最小值 + (P最大值 - P最小值) × (1 - exp(-P增长斜率 × 距离))
```

| 参数 | 作用 |
| --- | --- |
| P 最小值 | 目标接近中心时的基础移动强度 |
| P 最大值 | 目标较远时允许达到的最大移动强度 |
| P 增长斜率 | 从最小值增长到最大值的速度 |
| 框内位置 | 控制点在检测框内的垂直位置；顶部为 0%，底部为 100% |
| 视野半径 | 只选择以画面中心为圆心、该半径内的目标 |

目标选择规则是：先过滤目标标签，再过滤视野范围，最后选择控制点距离画面中心最近的目标。

以下设置可以在推理运行时立即生效：

- 目标标签。
- 触发方式。
- P 最小值、P 最大值和 P 增长斜率。
- 框内位置。
- 视野半径。

置信度、NMS IoU、模型和输入方式等设置在下一次启动时生效。

### 6.4 实时预览

实时预览显示：

- 输入画面。
- 全部检测框、标签编号和置信度。
- 当前选中目标及其控制点。
- 视野范围和画面中心。
- 推理耗时与完整检测耗时。

预览采用严格的按需策略：

- 未进入“实时预览”标签页时，不复制画面、不绘制检测框、不进行 JPEG 编码，也不发送预览数据。
- 切换到预览页后才开始处理预览。
- 离开预览页立即停止，并丢弃已经排队的旧预览帧。
- 关闭预览不会停止主推理流程。

预览绝不占用瞄准回路的时间：

- 渲染、JPEG 编码和发送全部在独立的后台线程完成，该线程优先级低于普通，永远不会
  抢主循环的 CPU。主循环只是把画面引用放进一个格子，实测耗时 0.004 毫秒
  （改造前同步渲染需要 0.78 毫秒，p95 0.98 毫秒）。
- 后台线程跟不上时直接丢掉过期画面，绝不让主循环排队等待。
- 预览按 30 帧/秒推送，界面每 16 毫秒取一次。取帧慢于推送会让画面步长忽长忽短，
  看上去一顿一顿——这正是早先界面挂在 80 毫秒消息泵上（12.5 Hz）时的表现。

## 7. 模型兼容策略

### 7.1 支持范围

- ONNX YOLOv5 原始检测输出。
- ONNX YOLOv8 原始检测输出。
- 每个候选为 6 列的端到端 NMS 输出。
- `[1,N,C]` 或 `[1,C,N]` 排列。
- 静态或动态候选数量。
- 常见多输出模型。

### 7.2 自动识别顺序

1. 读取模型输出节点及其形状。
2. 读取模型 `names` 元数据并获取类别数。
3. 使用类别数、格式特征列和输出形状确定检测张量。
4. 自动确定候选框轴和特征轴。
5. 信息不足时保留用户选择的输出格式，并对标签使用安全备用范围。

模型更换后会清除上一模型的检查结果，避免继续使用旧标签数量。

## 8. 延迟与性能

### 8.1 本机总延迟

UDP JPEG 模式显示的“接收端总延迟”从收到当前 JPEG 的第一个 UDP 分片开始，到完成识别、控制决策以及可能的 KMBox 发送为止。

它包括：

- UDP 分片重组。
- JPEG 解码与尺寸处理。
- 最新帧等待时间。
- 模型预处理。
- GPU/CPU 推理。
- YOLO 解码与 NMS。
- 实际发生时的 KMBox 发送。

它不包括：

- OBS 抓取画面的时间。
- OBS 或发送端 JPEG 编码时间。
- 第一个 UDP 分片到达前的网络传输时间。
- 显示器扫描和游戏内部响应时间。

若要测量真正的 OBS 到控制端延迟，需要发送端在每帧中附带统一时钟下的时间戳。

### 8.2 平均值与 P95

- **平均值**：统计周期内所有帧延迟的算术平均数。
- **P95**：95% 的帧延迟不高于该数值，剩余约 5% 的帧更慢。

优化实时控制时不能只看平均值。P95 能更好地反映偶发卡顿和延迟抖动。

### 8.3 性能建议

- 优先使用 TensorRT FP16。
- 使用与模型输入一致的发送尺寸，避免额外缩放。
- 使用 UDP JPEG 模式代替 OBS WebSocket 截图模式。
- 不查看画面时离开实时预览页。
- 使用“模型测速”至少运行 200 次，再比较平均值和 P95。
- 第一次使用 TensorRT 模型会创建引擎缓存，启动可能明显变慢；后续启动会复用缓存。
- 不应仅为了理论速度直接使用 INT8。需要代表性校准集，并验证检测召回率和定位精度后再决定。

### 8.4 标准管线测速

点击界面底部“管线测速”，或运行项目根目录的 `pipeline_benchmark.bat`，可以测试当前电脑、当前模型和当前输入配置下的完整接收端管线。

测速过程包含：

- 真实 UDP/OBS 输入与 JPEG 或视频解码。
- 最新帧等待。
- 模型预处理与推理。
- YOLO 输出解码和 NMS。
- 当前目标标签、框内位置和视野范围对应的目标选择。

测速开始前会进行模型预热和 30 帧真实画面预热。界面按钮采样 500 帧，批处理文件采样 1,000 帧。测速采用安全模式，不启用预览、不连接 KMBox，也不会发送鼠标移动。

控制台会分别显示每个阶段的平均值、P50、P95、P99 和最大值，同时显示处理帧率与跳过的旧帧数量。完整报告保存在 `.cache/benchmarks`，其中包含：

- 模型路径和 SHA-256 哈希。
- 实际启用的推理提供程序、CUDA Graph 和 GPU 预处理状态。
- 输入方式、尺寸和采集帧率。
- GPU、驱动、Python、OpenCV、NumPy 和 ONNX Runtime 版本。
- 汇总统计及每一帧的原始阶段耗时。

比较优化效果时，应在发送端画面、模型、输入尺寸和电脑负载相同的条件下分别运行测速，并优先比较 P95、P99 和跳帧数。

### 8.5 GPU JPEG 解码实测

2026-09-08 在当前验证环境中，使用 OBS 实际发送的 `320 x 320` JPEG 帧对 CPU 与 NVIDIA JPEG 解码路径进行了单帧测试。NVIDIA 测试组件为 `nvidia-nvimgcodec-cu12 0.9.0.20` 和 `nvidia-nvjpeg-cu12 12.4.0.76`。测试不使用批处理，以免批量等待人为增加实时控制延迟。

第一组测试使用相同的 1,000 帧 JPEG 数据，平均每帧约 13,481 字节：

| 解码路径 | 平均耗时 | P95 | 结果位置 |
| --- | ---: | ---: | --- |
| OpenCV/libjpeg-turbo | 0.420 ms | 0.847 ms | 系统内存中的 BGR 图像 |
| nvJPEG 默认混合路径 | 0.495 ms | 0.904 ms | 显存中的 BGR 图像 |
| nvJPEG 强制 GPU Huffman | 1.891 ms | 3.516 ms | 显存中的 BGR 图像 |
| nvJPEG 强制 GPU Huffman 后复制回系统内存 | 2.888 ms | 5.053 ms | 系统内存中的 BGR 图像 |

在 RTX 4060 Laptop GPU 上，纯 `GPU_ONLY` 解码器无法创建；可用的是 CPU/GPU 混合路径。NVIDIA 默认只对超过 1,000,000 像素的 JPEG 使用 GPU 混合 Huffman 解码，而当前一帧只有 102,400 像素。对于这样的较小图像，单独使用 GPU 解码并不比当前 CPU 解码快。强制 GPU Huffman 会明显增加平均耗时和延迟波动，因此不适合当前输入尺寸。阈值与解码选项参见 [NVIDIA nvImageCodec 官方文档](https://docs.nvidia.com/cuda/nvimagecodec/codec_options.html)。

第二组测试使用相同的 600 帧 JPEG 数据，并测量从 JPEG 字节到 TensorRT 输出的完整模型前段。GPU 路径复用固定显存缓冲，并将解码结果直接绑定为 TensorRT 输入：

| JPEG 到 TensorRT 输出路径 | 平均耗时 | P95 |
| --- | ---: | ---: |
| CPU 解码、上传显存、TensorRT | 1.738 ms | 2.886 ms |
| nvJPEG 混合解码、显存直连 TensorRT | 1.591 ms | 2.633 ms |

显存直连路径平均减少 `0.147 ms`，约为 `8.46%`；P95 减少 `0.253 ms`。收益来自省去 CPU 图像上传显存，而不是 JPEG 解码本身变快。

当前产品仍使用 OpenCV/libjpeg-turbo 在 CPU 上解码 JPEG。GPU JPEG 解码只完成了可行性验证，尚未接入正式流程。若后续实现，应作为可选功能并满足以下要求：

- 默认使用 NVIDIA 的自动混合策略，不强制 GPU Huffman。
- 复用固定的 GPU 输出缓冲，并直接连接 TensorRT 输入，避免复制回系统内存。
- 明确同步 JPEG 解码与 TensorRT 使用的 CUDA 流。
- NVIDIA 解码器不可用、输入格式不兼容或运行失败时，自动回退到当前 CPU 解码。
- 对检测框、置信度和标签选择进行回归验证；本次像素对比的平均绝对差约为 `0.58` 个灰度级，最大差为 `5` 个灰度级。

## 9. 配置文件

设置保存在项目根目录的 `settings.txt`。图形界面保存时会先写入临时文件、完成校验，再替换原文件，降低配置损坏风险。

| 分组 | 关键字段 | 说明 |
| --- | --- | --- |
| `input` | `mode` | `udp_jpeg`、`udp_video` 或 `obs_websocket` |
| `ui` | `language` | `zh` 或 `en` |
| `udp` | `host`、`port`、`width`、`height` | UDP 监听与处理尺寸 |
| `obs` | `host`、`port`、`password`、`source_name` | OBS WebSocket 参数 |
| `model` | `path`、`provider`、`cuda_graph`、`gpu_preprocess`、`output_format` | 模型文件、加速方式、CUDA Graph、GPU 预处理和输出格式 |
| `model` | `confidence`、`iou` | 检测过滤参数 |
| `kmbox` | `enabled`、`host`、`port`、`uuid` | KMBox 连接参数 |
| `aim` | `enabled`、`trigger`、`target_class` | 控制开关、触发键和目标标签 |
| `aim` | `target_y_ratio`、`fov_radius` | 框内控制点和视野范围 |
| `aim` | `kp_min`、`kp_max`、`kp_growth` | 动态 P 参数 |
| `aim` | `smoothing`、`deadzone`、`max_step` | 高级平滑、死区和单次移动上限；`deadzone` 按**准心到目标的误差像素**判定，误差小于该值即停止微调 |

`output_layout` 由程序强制设为 `auto`，不需要手动修改。

### 后台节流

窗口失去焦点后，Windows 11 会把进程丢进**效率模式（EcoQoS）**：挪到能效核、降频。
实测影响很不均匀——GPU 上的推理几乎不受影响（+5%），但 CPU 那几段明显变慢：

| 环节 | 前台 | 后台 | 变化 |
|---|---|---|---|
| 解码 | 0.46 ms | 0.64 ms | +39% |
| 后处理 | 0.24 ms | 0.39 ms | +67% |
| KMBox 发送 | 0.27 ms | 0.43 ms | +63% |
| 推理（GPU） | 1.77 ms | 1.84 ms | +5% |
| **总计 p99** | **6.2 ms** | **15.8 ms** | **+153%** |

管线启动时会自动申请：提高进程优先级、退出效率模式、把系统时钟精度设为 1ms。
启动日志里会显示这三项各自成功与否。

这一项还顺带避免了一类硬故障：KMBox 的 `timeout_seconds` 默认只有 **0.02 秒**，
被节流时查询按键状态很容易超时。

### 延迟日志

底部操作栏的**「记录延迟日志」**默认关闭。勾选后启动，程序会把**每一帧**的控制量
（看到的误差、发出的移动、当时有没有按瞄准键、锁定的是哪个目标）和各段耗时写进项目
目录下的 `latency-<时间戳>.csv`。

每帧都记而不是只记按键帧，有两个原因：各段耗时（解码、推理等）每帧都在测，跟按不按
瞄准键无关；而且发指令虽然需要按住瞄准键，**看响应不需要**——准心已经动了，目标还在
画面里，误差照样能测。

打 **3 次以上交火**就足够给出可信估计（有效配对不足时会自动放宽指令门槛）。注意小幅
微调不算数，必须是真正的甩枪：40 像素以内的移动一帧都不计入。

停止时会在日志框里直接给出估计，例如：

```
回路延迟 ≈ 3 帧 / 24.0 毫秒（帧间隔 8.00 毫秒，相关系数 0.973，可信）
  其中 AI 机侧 6.0 毫秒，游戏机+网络 ≈ 18.0 毫秒（含约 4.0 毫秒的系统性高估）
  依据 335 组拉枪配对（指令幅度 ≥ 6 像素）
```

原理：KMBox 一发指令准心立刻就动，但这个位移要绕完「渲染→截图→编码→网络→解码→推理」
一整圈才会出现在下一次看到的画面里。指令和误差响应之间差了几帧，就是整条回路的真实延迟。
**这个测法不需要在游戏机上装任何东西**——发指令走 KMBox 硬件，看结果走现成的画面流，
两端都在本机可观测。

三点限制：

- 延迟是**整数帧**，换算成毫秒有约半个帧间隔的系统性**高估**，「游戏机+网络」那一项尤其
  明显；用来判断瓶颈在哪一边够用，不要拿去做精确优化。
- 估计只用**拉枪那几帧**（指令 ≥ 6 像素）。控制器是对带噪测量值反应的，小指令里混着检测
  噪声，会把估计拽向 1 帧。拉枪太少时会自动放宽门槛（6→3→1）并降低可信度。
- 掉帧、换锁定目标、以及没检测到目标的帧都会被排除——那些时候误差的跳变不是我们发出的
  指令造成的（靠 `sequence` 和 `track_id` 两列识别）。
- 相关系数低于 0.6 会标注「偏弱」，多打几场再看。
- 报告会同时列出**次高峰**。两者越接近，说明延迟本身在这两个帧数之间抖动，
  这时候把结论当成一个精确整数是不对的。

### 对比多份日志

调 OBS 采集方式或参数时，用 `--analyze` 把几份日志并排看，不用跑一次读一次：

```
.venv\Scripts\python.exe -m rhodes_fast --analyze latency-A.csv latency-B.csv
```

输出每份日志的行数、回路帧数与毫秒、帧间隔、AI 机侧与游戏机侧耗时、相关系数、
配对数和丢帧数。

CSV 里还有一列 `skipped`：主循环跟不上时会直接跳到最新帧，中间那些帧被静默丢掉，
这一列记录每帧之前丢了多少。运行时每秒的状态行里也会显示累计`丢帧`。

## 10. 状态与故障处理

### 等待画面

检查：

- OBS 或发送端是否已经开始输出。
- 发送目标 IP 是否为运行 Endfield 的本机 IP。
- 发送端口和 Endfield 监听端口是否一致。
- 是否有其他程序占用了同一 UDP 端口。
- Windows 防火墙是否允许对应 UDP 流量。

### 模型无法读取

检查：

- 模型路径是否存在。
- 文件是否为有效 ONNX 模型。
- 输出是否为受支持的三维检测张量。
- 输出格式是否与模型导出方式一致。

### TensorRT 首次启动较慢

这是首次构建引擎缓存的正常现象。等待构建完成，不要重复启动多个 Endfield 实例。缓存位于项目的 `.cache/tensorrt`。

### 识别正常但没有移动

检查：

- 是否启用了 KMBox 控制和目标控制。
- KMBox 地址、端口及 UUID 是否正确。
- 当前目标标签是否与预览中的标签一致。
- 目标控制点是否位于视野半径内。
- 是否按住了配置的触发键。
- P 参数是否过小，或移动量是否落在死区内。

### 预览没有画面

预览只在“实时预览”页处理。先启动主流程，再进入该标签页。如果主流程仍显示“等待画面”，应先排查输入连接。

## 11. 验收清单

发布或更换模型后，建议依次验证：

1. 图形界面能够正常打开，设置文件能够加载。
2. 模型检查显示正确的格式、输出尺寸和标签范围。
3. “测试输入”能够收到预期尺寸的画面。
4. KMBox 能够连接，且关闭控制时不会发送移动。
5. 标签 `0、1、2…` 分别测试时，只跟踪当前选中标签。
6. 四种触发键分别能够触发控制。
7. 框内位置、视野半径和动态 P 参数能在运行中更新。
8. 实时预览页能够显示检测框，离开页面后立即停止预览处理。
9. 连续运行时无明显队列累积，处理帧率和 P95 延迟稳定。
10. 停止按钮能够结束推理子进程并释放 UDP 端口。

## 12. 数据与使用边界

Endfield 默认在本机运行，不主动上传模型、画面或配置。UDP 和 KMBox 数据是否经过局域网取决于用户的网络拓扑。

请仅在获得授权的设备、软件和测试环境中使用，并遵守目标软件、平台及所在地区的规则。
