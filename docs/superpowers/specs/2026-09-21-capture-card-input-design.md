## 1. 背景与目标

双机方案里，画面现在靠 UDP 或 OBS 从主机传过来。**目标**：把游戏机的 HDMI 接到采集卡上，由副机直接读采集卡。

用户的卡是 **AVerMedia Live Gamer ULTRA 2.1（GC553G2）**。按厂商规格：

- USB 3.2 Gen2 Type-C（10 Gbps），是标准 UVC 设备，免驱，OBS 等第三方软件都能直接读；
- 画面格式有 YUY2、NV12、RGB24、P010（HDR）、MJPEG；
- Windows 下最高采集 2160p144；直通最高 2160p144 / 1440p240 / 1080p360。

用户手册第 14 页「Capture Capability Breakdown by Video Format」，跟本项目有关的几行（单位 fps）：

| 采集分辨率 | 格式 | USB 3.2 Gen2（10 Gbps） | USB 3.2 Gen1（5 Gbps） |
|---|---|---|---|
| 2560×1440 | NV12 | 144 / 120 / 60 | 60 |
| 2560×1440 | YUY2 | 60 | 50 |
| 2560×1440 | MJPEG | 144 / 120 / 60 | 144 / 120 / 60 |
| 1920×1080 | NV12 | 240 / 120 / 60 | 120 / 60 |
| 1920×1080 | YUY2 | 120 / 60 | 60 |
| 1920×1080 | MJPEG | 240 / 120 / 60 | 240 / 120 / 60 |

所以这张卡能**不压缩地（NV12）采到 1440p144 或 1080p240**，前提是接在 10 Gbps 的口上：接 5 Gbps 的口，1440p 的 NV12 只剩 60。

**用户已定**：只截取画面正中央一块，尺寸由用户设置，默认 320×320。

**实机探测（2026-09-21，卡接在 ThinkBook 16p G4 IRH 上）**，跟手册对不上的地方以实机为准：

- 卡通过 DirectShow 报出来的 NV12 档位：1920×1080 最高 **240**，2560×1440 最高 **120**（手册写 144）。按手册，1080p NV12 240 只有 10 Gbps 的口才有，所以链路确实是 10 Gbps。
- **要 2560×1440@144 直接打不开**（`OSError: I/O error`）。这版固件在 DirectShow 下没有 1440p144，可能要在 AVerMedia Gaming Utility 里升级固件才有。
- **DirectShow 下一个 MJPEG 档都没有**，只有 NV12 和 YUY2（yuyv422）。
- 卡声明的颜色是 **BT.709、有限范围**（`tv, bt709/bt709`）。第 3.2 节的颜色转换按它来，不用 cv2 默认的 BT.601。
- 平面行宽等于画面宽（`line_size` = 1920 / 2560），没有行尾填充；但代码仍按 `line_size` 排行，换卡或者换驱动就可能有填充。
- 没有 HDMI 信号时，卡照样出帧：全黑（中央平均亮度 3 左右），几乎全是重复帧，帧率也不准（要 240 实收 83）。**测速一定要在有信号时做**。
- 笔记本的雷电 4 口单独占一个控制器，其余 USB 口（包括扩展坞）都挤在芯片组那一个上。卡应该插雷电 4 口；探测时卡插在芯片组那一侧的 10 Gbps 口上。

### 1.1 延迟最低的配置

采集卡这一段的延迟由三件事决定，按影响从大到小：

1. **帧周期**。卡要收完（至少大半）一帧才往 USB 上送，USB 也要把这一帧传完主机才拿得到。两段都跟帧周期成正比：144 fps 一帧 6.9 ms，240 fps 一帧 4.2 ms，60 fps 一帧 16.7 ms。按「一到两个帧周期」粗估：1080p240 约 4–8 ms，1440p144 约 7–14 ms，任何 60 fps 的档约 17–33 ms。**这是估算，必须实测（第 8 节）**。
2. **压缩**。MJPEG 要卡上先编码、主机上再把整帧解码一遍（1440p 一帧就是 370 万像素），只能整帧解完再截取。**NV12** 不压缩，主机上只截中央一小块转颜色，不到 1 ms。YUY2 同样不压缩，但带宽大一半，这张卡上的档位都比 NV12 低。
3. **信号本身多久出一帧**。卡采得再快，游戏机输出的 HDMI 信号是 144 Hz 的话，新画面也只是每 6.9 ms 一张。

结论（写进界面和 README）：

- **格式选 NV12，帧率选卡在这个分辨率下的最高档**：1080p 选 240，1440p 选 144。采得比信号快不吃亏：多出来的是重复帧，由第 3.4 节丢掉；而采得越快，一张新画面等到被采的时间越短。
- **首选 1080p240 NV12**。实机上 1440p NV12 最高只有 120（一帧 8.3 ms），1080p240 一帧 4.2 ms，差了一倍。代价是游戏如果是 1440p，卡要把它缩成 1080p，中央 320×320 对应游戏里 427×427 的一片，目标看起来小了 0.75 倍，算法参数要重调。能不能在 1440p 信号下采 1080p，要接上信号确认。
- **游戏机的输出刷新率拉到卡的采集档**（1440p 就 144 Hz，1080p 就 240 Hz）；关掉那个输出的 VRR（G-Sync / FreeSync），游戏里关垂直同步。
- **卡接在 10 Gbps 的 USB-C 口上**，直连主机，不经过扩展坞或集线器。
- **HDR 关掉**：P010 的档位最高只有 60 / 120，而且本设计只读 SDR。

## 2. 读卡用什么：PyAV（dshow）

两条可选的路都在现有依赖里，不加新包：

| | PyAV + FFmpeg dshow | OpenCV VideoCapture（DSHOW / MSMF） |
|---|---|---|
| 列出设备名 | ✅ `list_devices`（实测：本机列出了 Integrated Camera、OBS Virtual Camera） | ❌ 只有编号 |
| 列出设备支持的模式 | ✅ `list_options` | ❌ |
| 拿到 NV12 原始数据 | ✅ 按平面拿，可以**先截取再转颜色** | 默认把整帧转成 BGR：1440p144 每帧都转整张，CPU 吃不消 |
| 项目里已经在用 | ✅ UDP 视频流那一路就是它 | 只用来解 JPEG |

选 **PyAV**。同类项目（如 sunone_aimbot_cpp）用 OpenCV 读视频设备，但它们要的是整帧，我们只要中央一小块，能先截取再转颜色是决定性的。

## 3. `CaptureCardSource`

新文件 `rhodes_fast/capture_card_source.py`，实现 `FrameSource`，结构照抄 `UdpSource` / `DesktopSource`：一条守护线程一直读，只留最新一帧，不排队。

### 3.1 打开设备

```python
av.open(f"video={device}", format="dshow", options={
    "video_size": "2560x1440",
    "framerate": "144",
    "pixel_format": "nv12",      # MJPEG 时换成 "vcodec": "mjpeg"
    "rtbufsize": str(一帧字节数 × 4),
})
```

- **`rtbufsize` 必须设**：dshow 默认的实时缓冲只有约 3 MB，比一帧 1440p NV12（约 5.5 MB）还小，FFmpeg 会一直报缓冲满、丢帧。设成 4 帧大小。
- **不会因此积压延迟**：读线程只做「取一帧 → 截取 → 转颜色 → 发布」，每帧不到 1 ms，远快于 144 Hz 的出帧间隔（6.9 ms）。积压只会发生在读的人跟不上的时候，而读线程和推理是分开的。
- 设备名为空时用列出来的第一个视频设备。

### 3.2 先截取再转颜色

`capture_region(frame_w, frame_h, width, height)` 直接用单机模式那一个（正中央，比画面大就报错不裁剪）。**截取区的左上角和宽高都要取偶数**：NV12 和 YUY2 的色度是两个像素共用一份，从奇数位置切会把颜色切错位。

| 格式 | 做法 |
|---|---|
| NV12 | Y 平面切 `height × width`，UV 平面切 `height/2 × width`（UV 是交错存的，列范围和 Y 一样），再按 **BT.709 有限范围**转成 BGR（卡声明的就是这个；320×320 的一小块，自己按矩阵算也不到 1 ms）。不用 `cv2.cvtColor(..., COLOR_YUV2BGR_NV12)`：它按 BT.601 算，颜色会偏 |
| YUY2 | 打包格式，一行 `2×宽` 字节：切行、切 `[left×2 : (left+width)×2]` 列，`COLOR_YUV2BGR_YUY2` |
| MJPEG | 只能先整帧解码，再整帧转 BGR、再截取。CPU 开销大，只作兜底，界面上标出来 |

平面数据用 `np.frombuffer(plane, uint8).reshape(行数, plane.line_size)` 零拷贝拿，注意 `line_size` 可能比宽度大（行尾有对齐填充），先按 `line_size` 排行再切列。

### 3.3 时间戳

`first_packet_at` 取 PyAV 交出这一帧的时刻，`decode_ms` = 截取和转颜色的耗时，`assembly_ms` = 0。

采集卡自己的延迟（HDMI 进卡 → 编码 → USB → 驱动）在进程里量不到：dshow 给的 `pts` 是 DirectShow 参考时钟，跟 `perf_counter` 对不上。要量卡的延迟，用现有的轨迹功能：它会自动估算「指令发出 → 画面上看到」隔了几帧，这个数**包含**采集卡的延迟。拿它跟 UDP 那一路比，差值就是换成采集卡多出来的延迟。

### 3.4 重复帧

卡采得比 HDMI 信号快时（比如信号 144 Hz、卡采 240），有些「新帧」其实是上一张画面原样再发一次。把它当新帧往下送，速度类算法（前馈、在途补偿）会看到目标在这几毫秒里一动不动，速度估计被拉低，手感发涩。

处理：**截取之后跟上一帧的截取逐字节比较，完全一样就不发布**，就像本机屏幕那边画面没变时 `grab` 返回 `None`。不压缩的数字信号，重复帧是逐字节相同的；320×320 比一次大约几十微秒。游戏画面真的完全静止时也会被跳过，那几帧本来就没有新信息。

读线程顺带数一下重复帧占多少，连接测试打出来（`重复帧 40%` 就说明信号刷新率比采集帧率低，该去调游戏机的输出）。

### 3.5 出错与重连

拔线、换分辨率、游戏机休眠都会让读流中断。照 `UdpSource._run`：捕获异常写进 `error`，等 0.5 秒，关掉容器再重新打开。

## 4. 列出设备和模式

新增两个纯函数（解析）加两个薄壳（调 PyAV），放在同一个文件里：

```python
def list_capture_devices() -> list[str]               # 只要视频设备，不要音频
def list_device_modes(device: str) -> list[CaptureMode]  # (格式, 宽, 高, 最低帧率, 最高帧率)
def parse_device_list(messages: list[str]) -> list[str]
def parse_device_modes(messages: list[str]) -> list[CaptureMode]
```

- 用 `av.logging.set_level(INFO)` 加 `av.logging.Capture()` 收 FFmpeg 的日志，`av.open(..., options={"list_devices": "true"})` 会抛 `ExitError`，这是正常的。**实测**：日志是一段一段来的（`'"Integrated Camera"'`、`'(video'`、`')'` 分成三条），要先拼起来再按行解析。设备名里可能有 `®` 这类字符，打印时注意编码。
- 模式行形如 `pixel_format=nv12  min s=2560x1440 fps=60 max s=2560x1440 fps=144` 或 `vcodec=mjpeg ...`，用正则解析。
- 解析函数吃字符串列表，单元测试不需要真设备。
- 用完把 FFmpeg 的日志级别恢复原样，不然 UDP 那一路之后会满屏刷 INFO。

## 5. 配置、预设、界面

### 5.1 配置

```python
@dataclass(frozen=True, slots=True)
class CaptureCardConfig:
    device: str = ""              # 空 = 第一个视频设备
    video_size: str = "1920x1080" # 向卡要的分辨率
    framerate: float = 60.0
    pixel_format: str = "nv12"    # "nv12" | "yuyv422" | "mjpeg"
    width: int = 320              # 截取尺寸, 用户设置
    height: int = 320
```

- `input.mode` 加 `"capture_card"`。
- 默认 1920×1080@60 是因为这是最通用的档，用户的游戏分辨率不知道。README 和界面提示都说清楚：**改成游戏的分辨率**，截取才是 1:1 的像素；帧率选卡在这个分辨率下支持的最高档。
- 校验：`video_size` 形如 `宽x高`；帧率 > 0；格式在集合里；截取宽高为正偶数。
- `AppConfig` 在末尾加 `capture_card: CaptureCardConfig = field(default_factory=...)`；老文件没有这一节时按默认值读。

### 5.2 预设

`_WIRING_FIELDS` 加 `capture_card: (device, video_size, framerate, pixel_format, width, height)`，**老预设缺这一节按默认读**，跟 `desktop` 同一种写法。

### 5.3 界面（01 运行设置 → 画面输入）

输入方式下拉框加一项「采集卡」，选中时显示 `#capture-panel`：

- **设备**：下拉框，旁边一个「刷新」按钮。选项来自 `list_capture_devices()`，由 Python 用 `setChoices` 推过去；`settings.txt` 里存的设备现在不在的话，也留在选项里（后面标「未连接」），不让它悄悄跳到别的设备上。
- **采集模式**：一个下拉框，选项来自 `list_device_modes()`，每个「格式 + 分辨率」一项，帧率取这一档的最高值，比如 `1920x1080 · 240 fps · NV12`。不压缩格式里帧率最高的那一项后面标「（延迟最低）」，MJPEG 的标「（CPU 开销大）」。选中后写回 `video_size` / `framerate` / `pixel_format` 三个字段。设备没插着的时候，只显示设置里存的那一项。
  - 用下拉框而不是三个自由填写的格子：随手填的组合卡多半不支持，打开时才报错，而且报的是 FFmpeg 的原话。
- **截取尺寸** 宽 × 高，默认 320 × 320。
- 一行提示：按游戏的分辨率采，截取才是 1:1；游戏开着 HDR 的话，关掉或者让卡输出 SDR。

旧 tkinter 界面照单机模式的做法，只保证不出错：选「采集卡」时藏起 UDP 和 OBS 两组，保存时 `[capture_card]` 原样保留。

「测试输入」对采集卡：

采集卡 正常：画面=320x320 · 信号=2560x1440@144 · 格式=nv12 · 设备=Live Gamer ULTRA 2.1

## 7. 测试（单元，TDD）

| 测试 | 钉住什么 |
|---|---|
| NV12 截取：造一帧已知 Y/UV 的 NV12，截中央，转出来的 BGR 跟整帧转完再截的结果一致 | 平面切法写错，颜色错位或整块发绿 |
| `line_size` 大于宽度（带填充）时照样切对 | 真卡常带对齐填充，按宽度排行会整帧斜掉 |
| YUY2 截取，同上 | 打包格式的列要乘 2 |
| 截取区左上角是奇数时向下取偶 | 色度错一个像素，边缘出彩边 |
| 截取区比信号大 → 报错不裁剪 | 同单机模式 |
| 设备列表解析：分段来的日志拼起来、只要 video、不要 audio 和 Alternative name 行 | 实测日志就是分段的 |
| 模式列表解析：pixel_format 和 vcodec 两种行都认 | |
| 打开时带上 `rtbufsize`，而且至少能放下 1 帧 | 不设会一直丢帧 |
| 截取跟上一帧逐字节相同 → 不发布，并计入重复帧 | 重复帧会把速度估计拉低 |
| 读流中断后重开 | 拔线、换分辨率之后画面永久停住 |
| `stop()` 关掉容器、结束线程 | 设备被占住，下次打不开 |
| 配置 / 预设：老文件没有 `[capture_card]` 照常读；新字段往返不丢 | |
| 连接测试：打的是实际协商出来的信号，和设置不一致时警告 | |
| 状态灯认两句新话 | |

读流部分用假容器（按脚本吐假帧）测，跟 `DesktopSource` 用假 camera 同一个思路。

## 8. 实机验证

需要把卡接到跑本程序的电脑上，USB 口要是 10 Gbps 的（USB 3.2 Gen2 或雷电口）。

1. 列设备、列模式，对照第 1 节的表确认 USB 口是 10 Gbps（1440p 的 NV12 能选到 144 才算）。
2. 1440p144 NV12 和 1080p240 NV12 各采 30 秒：实际帧率、重复帧比例、截取加转颜色的耗时、读线程的 CPU 占用。
3. 管线测速（`--pipeline-benchmark`）。
4. 延迟对比：同一个游戏、同一套方案，分别用 UDP、1440p144、1080p240，看轨迹估算出来的回路延迟帧数。帧数是按帧量化的，只能看出差一两帧的大差别。

## 9. 风险

- **卡本身的延迟**是这条路最大的未知数，进程里量不到，只能用第 8 节第 4 项间接比出来。
- **HDR**：游戏或 Windows 开了 HDR 时，卡给的可能是 P010，或者颜色发灰。本设计只读 SDR 的 NV12 / YUY2，界面和 README 上提示关掉 HDR。
- **颜色矩阵**：卡声明 BT.709 有限范围，第 3.2 节按它转。UDP 视频流那一路现在由 swscale 转，用的矩阵可能不同，两路出来的颜色可能有细微差别；实测识别率明显不一样时再对齐。
- **USB 口带宽**：接在 5 Gbps 的口上，1440p144 的 NV12 带宽不够，卡会协商成更低的帧率。连接测试会把实际帧率打出来。

## 10. 明确不做

- 采集卡的音频。
- HDR（P010）采集。
- 按窗口或按任意位置截取；截取永远是画面正中央。
- 旧 tkinter 界面的新控件。

## 实测记录（2026-09-21）

### 被动测量：游戏机输出 1440p144，卡插雷电 4 口，每档 6 秒，画面在动

「新画面」= 整帧 Y 平面（每 8 像素取 1）跟上一帧不同。

| 采集档（NV12） | 卡给的帧率 | 新画面 | 新画面间隔 P50 / P95 |
|---|---|---|---|
| **1920×1080 @ 240** | 208 fps | **137 张/秒** | 8.6 / 10.0 ms |
| 2560×1440 @ 120 | 61 fps | 46 张/秒 | 17.5 / 34.4 ms |
| 1920×1080 @ 120 | 109 fps | 101 张/秒 | 9.0 / 17.8 ms |

- **1080p240 基本拿全了 144 Hz 信号的每一张新画面**（240/144 = 1.67，新画面落在 1 或 2 个采集周期上，P50 是 2 个周期 8.3 ms）。卡能把 1440p 的信号缩成 1080p 再采。
- **1440p 档在 144 Hz 信号下只给 61 fps**，比它报的 120 还少一半，不能用。
- 所以这张卡**选 1080p240 NV12**，中央截取 320×320 对应游戏里 427×427。

### 读卡方式：同为 1080p240 NV12，每种 6 秒

| 方式 | 卡给的帧率 | 新画面 | CPU（一个核 = 100%） |
|---|---|---|---|
| **PyAV dshow，直接读包** | 203 fps | 136 张/秒 | **28%** |
| PyAV dshow，读包后 `packet.decode()` | 208 fps | 137 张/秒 | 226% |
| OpenCV DSHOW（要原始数据） | 104 fps | 93 张/秒 | 18%（但给回来的已是整帧 BGR） |
| OpenCV MSMF | 编号 0–3 都打不开这张卡 | | |

- **不调 `decode()`**：rawvideo 解码本身只要 0.02 ms，但 CPU 从 28% 涨到 226%，多出来的是 FFmpeg 为它开的线程。实现时从 `packet` 的缓冲区直接切（`np.frombuffer(packet)`，零拷贝），包大小实测正好是 `宽×高×1.5`（1080p 3110400 字节），没有行尾填充。
- 切中央 320×320 加转颜色每帧 0.48 ms。
- OpenCV DSHOW 要原始数据也还是返回整帧 BGR，而且丢了一半的帧。

### 前两次延迟测试没有得到可用数据（第四版测成了，见下一节）

1. **KMBox 端到端**（发移动 → 游戏机光标动 → 卡上看到变化）：当时游戏机画面整屏在动，120 次里只有 7 次等到了静止，检测到的变化都是整屏宽，不是光标。数据作废。
2. **HDMI 回环**（笔记本 HDMI → 卡，屏幕中央方块变色，DXGI 出帧时间对卡上到达时间）：每档 50 次变色只对上 1–17 次，中位 45–52 ms，还出现了 0.97 ms 这种不可能的值，是配对错了。当时笔记本是**复制屏幕**模式（LG 4K240、采集卡、内屏同一个桌面），DXGI 报的出帧时刻跟 HDMI 实际发出的时刻对不上。数据作废。

重测要改的：卡作为**单独的扩展屏**（不复制），方块只画在这块屏上；每次的原始时间写进文件，不只打印汇总；先核对两边检测到的变色次数都接近 50 次再算延迟。

### HDMI 回环延迟（第四版，有效）

笔记本只接采集卡一块屏（RTX 4060 直出 HDMI，没有复制屏幕），模拟游戏机的输出。屏幕中央一个方块深灰 / 浅灰交替，每档 80 次：

- 方块用 Win32 直接画，画完 `DwmFlush()`；它在桌面合成真正提交这一帧时返回，这个时刻当「出帧」。实测合成有时要隔几秒才提交（画上去 318 ms，提交 3057 ms，卡上 3084 ms 看到），所以**必须从提交时刻算**，从「画上去」算会整体错开。
- 读卡单独一个进程，直接读包。两个进程都用 `perf_counter`（QPC，全系统同一个时钟）。
- 配对：第 k 次切换只在「它提交之后、第 k+1 次提交之后 100 ms 以内」找同色的变化，找不到就跳过，不连累后面。
- 延迟 = 卡上看到的时刻 − 提交时刻，包含：等扫描输出 → HDMI → 卡收帧 / 缩放 → USB → 驱动 → FFmpeg → 我们读到。游戏机那边从游戏出帧到 HDMI 送出的那一段同样存在。

| 输入（笔记本输出） | 采集档（NV12） | 中位 | P10 / P90 | 样本 |
|---|---|---|---|---|
| 2560×1440 @ 144 | **1920×1080 @ 240** | **27.7 ms** | 20.4 / 35.8 | 71 |
| 2560×1440 @ 144 | 1920×1080 @ 120 | 33.9 ms | 26.2 / 42.3 | 79 |
| 2560×1440 @ 144 | 2560×1440 @ 120 | 45.7 ms | 28.6 / 69.1 | 79 |
| 1920×1080 @ 144 | **1920×1080 @ 240** | **27.3 ms** | **25.3 / 29.2** | 79 |
| 1920×1080 @ 144 | 1920×1080 @ 120 | 37.0 ms | 32.8 / 42.3 | 79 |

结论：

- **1080p240 最低**，比 120 帧的档低 6–10 ms，比 1440p120 低 18 ms。
- **输入也是 1080p 时最稳**：P10–P90 只差 4 ms。1440p 输入要卡先缩放，中位数一样，但波动大了一倍（20–36 ms）。所以游戏机输出 1080p 更好，模型看到的范围不变（见第 1.1 节的换算）。
- 这张卡从笔记本能设的最高刷新率是 144 Hz，**240 Hz 输入没测到**。
- 跟双机 UDP 比：本机 DXGI 抓屏从出帧到拿到数据只要 1.6 ms，加上压缩和网络大约 5 ms。**采集卡这条路大约多 22 ms**，换来的是游戏机上不用跑任何采集程序。

原始数据：会话临时目录下的 `card_loopback4_raw.json`（每次切换的画上去 / 提交时刻，每次卡上变化的到达时刻和亮度）。
