# 瞄准算法插件化 —— 设计文档

日期：2026-09-11

## 背景

目前的移动控制是写死在 `KmboxController.move_toward` 里的一套：动态 kp 的纯比例控制，
外加 EMA 平滑、死区、亚像素累加、限幅。想试别的控制律只能改源码，改完也没法回退对比。

仿真显示现有算法在实测的 7~8 帧回路延迟下有明显问题：100px 拉枪超调 43.6px，
稳定要 180ms。几种改进方案各有取舍（见附录数据），但**哪个手感更好只能靠实际打过才知道**——
这一点后来验证了：实机试出来最好的是 `feedforward`，而仿真综合分最高的 `inflight_ff` 跟不上人。

更重要的是，用户希望这套控制算法能由社区共同演进：任何人实现了新算法（卡尔曼滤波、
完整 PID、自适应增益……）都能分享给别人用，而不是只能在固定框架里调几个参数。

## 目标

1. 控制算法成为可插拔单元，内置与用户自定义走**同一套契约**
2. 每个控制方案独立选择算法，两个触发键即两个算法，游戏中按不同键即可对比手感
3. 支持分享：调校参数用 JSON，算法实现用独立 .py
4. 界面上能导入、查看源码、改名、删除算法
5. 不影响瞄准回路性能

## 非目标

- **不做**控制质量的自动测量（超调、稳定时间等指标）。本期靠手感判断。
  现有 `--analyze` 测的是回路延迟，那是采集链路的属性，换控制算法不会改变它，
  拿它对比算法会得到两边一样的数字。
- **不做**热切换。算法在管线启动时加载，改算法需重启。
- **不做**沙箱化。见「安全」一节。

## 安全

**运行他人分享的算法无法在技术上做成安全的。** 算法跑在 4ms 的热循环里：
进程隔离每帧一次 IPC 会吃光延迟预算；`RestrictedPython` 之类挡不住有意为之的人，
还会让 numpy 这种正常依赖变得很麻烦。

因此安全靠**流程**而非技术边界，设计上守住两条：

1. **导入调校 JSON 绝不执行任何代码。** 装算法和导入调校是两件独立的事。
2. **确认在执行之前。** 选文件、看源码、点确认这三步都不加载模块；
   只有用户明确点了「确定导入」之后才复制文件并 import 校验。

## 架构

### 插件契约

新增 `rhodes_fast/aim_algorithms/` 包：

```python
@dataclass(frozen=True, slots=True)
class Param:
    name: str
    default: float
    minimum: float
    maximum: float
    label: str          # 界面上显示的中文名

@dataclass(frozen=True, slots=True)
class Observation:
    error_x: float             # 当前误差（像素）
    error_y: float
    dt: float                  # 距上一帧的秒数，不要假设固定帧率
    frame_index: int
    recent_commands: Sequence[tuple[int, int]]   # 最近发出的移动量，最新的在末尾
    kp_min: float              # 该方案的 kp 参数，算法想用就用
    kp_max: float
    kp_growth: float

class Algorithm(Protocol):
    NAME: str                  # 稳定标识，调校 JSON 引用它
    DISPLAY_NAME: str
    PARAMS: tuple[Param, ...]  # 自声明参数，界面据此生成输入框

    def __init__(self, params: Mapping[str, float]) -> None: ...
    def reset(self) -> None: ...
    def compute(self, observation: Observation) -> tuple[float, float]: ...
```

`compute` 返回**这一帧想走多少像素**（浮点）。取整、限幅、发送都不归它管。

`recent_commands` 至少保留 64 帧。这是写「扣在途」「前馈」「卡尔曼」的必要信息：
算法结合自己的 `loop_delay_frames` 参数，既能算出在途未生效的指令总量，
也能算出本帧刚生效的那条指令，从而把目标自身的位移和我们的位移区分开。

### 边界：算法管什么，管道管什么

| 归算法 | 归共用管道（`move_toward`） |
|---|---|
| 误差 → 想走多少像素 | 算误差（目标点 − 画面中心） |
| 自己的内部状态 | 死区判定 |
| | EMA 平滑 + 符号翻转清零 |
| | 亚像素累加器 |
| | `max_step` 限幅 |
| | 发送 KMBox、异常兜底 |
| | 切换方案 / 丢失目标时调 `reset()` |

**内置算法不开后门**，和自定义算法走完全相同的契约。如果某个内置算法需要特殊通道，
说明契约设计得不对。

### 性能

每帧新增开销：一次注册表查找 + 一次方法调用 + 算法内部计算（最重的「扣在途」是
不超过 64 个浮点数求和）。相比实测的 0.32ms Python 胶水开销可以忽略。

`Observation` 每帧新建一个 frozen dataclass；`recent_commands` 用 `collections.deque(maxlen=64)`，
只传引用不拷贝。

## 内置算法

| NAME | 说明 | 参数 |
|---|---|---|
| `p` | 现状：`误差 × 动态kp` | 无 |
| `pd` | 加 `kd × (误差 − 上帧误差)` | `kd` |
| `feedforward` | 误差上叠加 `目标速度 × 延迟帧数` | `loop_delay_frames`, `gain`, `velocity_smoothing` |
| `inflight` | 误差减去已发出但未生效的指令 | `loop_delay_frames` |
| `inflight_ff` | 上面两者合用 | `loop_delay_frames`, `gain`, `velocity_smoothing` |

默认算法是 `p`，保持现有手感不变。

## 配置

`AimProfileConfig` 新增两个字段：

```python
algorithm: str = "p"
algorithm_params: dict[str, float] = field(default_factory=dict)
```

存储需要改动 `config.py` 两处：

- `_convert_section`：类型提示是 dict 时用 `json.loads` 解析（INI 路径专用）
- `_write_config` 的 INI 分支：dict 值用 `json.dumps` 而不是 `str()`，
  否则写出的是 Python repr（单引号），读回来 `json.loads` 会失败

TOML 路径不用改，`tomli_w` 原生支持嵌套表。

`settings.txt` 里的样子：

```ini
[aim_profile_1]
algorithm = inflight_ff
algorithm_params = {"loop_delay_frames": 8, "gain": 1.0, "velocity_smoothing": 0.25}
kp_min = 0.14
kp_max = 0.35
```

未在 `algorithm_params` 里出现的参数取 `PARAMS` 里声明的默认值。

## 分享

### 调校 JSON

```json
{
  "format": 1,
  "algorithm": "inflight_ff",
  "params": { "loop_delay_frames": 8, "gain": 1.0, "velocity_smoothing": 0.25 },
  "kp_min": 0.14,
  "kp_max": 0.35,
  "kp_growth": 0.031,
  "target_y_ratio": 0.08,
  "fov_radius": 150.0,
  "measured_loop_ms": 33.3
}
```

设计要点：

- **不含 `trigger` 和 `target_class`。** 按键习惯因人而异，目标标签取决于用哪个模型。
  导入只覆盖手感调校那几项。
- **`params` 是字典**，因此能装任何插件自声明的参数，不需要预先知道有哪些。
- **`measured_loop_ms` 是作者机器的实测回路延迟。** 导入时和本机最近一次实测值比对，
  差距超过一帧就提示：作者的延迟和你差 XX ms，扣在途/前馈的补偿量可能不合适。
  这是必要的——仿真显示假设 L=8 但真实 L=4 时，稳定帧数从 15 涨到 35。
- 导入时算法名解析不到就**明确报错**（「这份调校需要 `my_kalman`，你还没装」），
  绝不静默回退到默认算法。静默回退会让人以为在用对方的调校，实际手感完全不同。
- `format` 版本号不认识时报错，不猜测。

### 算法实现

自定义算法是 `algorithms/` 目录下的独立 .py，该目录与 `settings.txt` 同级（项目根目录）。
分享 = 把 .py 和调校 JSON 一起发。

内置算法随程序分发，在 `rhodes_fast/aim_algorithms/` 包内，**不出现在 `algorithms/` 目录
也不出现在注册表里**，因此不可删除、不可改名。列表里两者混在一起显示，但内置的标注「内置」。

## 算法库管理

界面新增「算法库」区域，列出已装算法（显示名、作者、来源文件、导入日期）。

### 导入流程

顺序是这个流程唯一的意义所在：

1. 选文件 —— **不执行任何代码**
2. 确认框：文件名、大小、作者信息，带「查看源码」按钮（可选）
3. 用户点「确定导入」
4. **此时才**复制到 `algorithms/` 并 import 校验
5. 校验不通过（无合法 `Algorithm` 类、缺 `NAME`、`compute` 签名不符）则删除并报错
6. 提示「导入成功，下次启动后可用」

### 管理操作

查看源码 / 改名 / 删除。

**改名只改显示名，不动文件里的 `NAME`：**

| | 存在哪 | 可改 |
|---|---|---|
| `NAME`（标识） | .py 文件内 | 否。改了别人发来的调校就对不上 |
| 显示名 | `algorithms/installed.json` | 是 |

注册表 `algorithms/installed.json` 记录每个算法的显示名、来源文件、导入时间。
删除即删 .py 与对应条目。

**重名冲突**：导入时 `NAME` 与已装的相同，提示「已存在同名算法 X（来自 yyy.py），
要替换吗」，不静默覆盖。

### 生效时机

算法在管线**启动时**加载。刚导入的算法下次启动才能用。

**配置里的算法在启动时不存在**（例如删掉了 .py 但配置还指着它）：打印醒目错误
并回退到 `p`，不阻止管线启动。这里和导入调校的处理不同是有意的——导入是交互式的，
可以让用户当场修正；启动失败则会让人在游戏里发现自瞄整个不工作，更糟。
但回退必须**响亮**，日志框里要明确写出「算法 X 找不到，已回退到 p」。

界面上算法下拉框在运行中禁用，旁注「停止后可改」。kp 保持现有的热更新行为（调手感需要）。

## 测试策略

走 TDD，每项改动先写能复现问题的失败测试。

**算法本身**（纯函数，最好测）：给定误差序列断言输出序列。
每个内置算法覆盖：零误差、单步阶跃、匀速目标、目标突然反向。

**回归保护**（最重要的一条）：`p` 算法的逐帧输出必须与重构前的 `move_toward` 完全一致。
用现有的 `tests/test_kmbox_control.py` 既有用例作为基准。

**共用管道**：死区、亚像素累加、限幅的行为不随算法改变。

**配置**：`algorithm_params` 在 `settings.txt`（INI）与 `config.toml`（TOML）两条路径上
的往返一致性。

**分享**：调校 JSON 往返一致；缺算法时报错；`format` 版本不认识时报错；
`measured_loop_ms` 差距大时给出提示。

**算法库**：导入校验拒绝非法文件；确认之前不加载模块（用 mock 断言 import 未被调用）；
重名冲突提示；改名不影响 `NAME`；删除清理干净。

## 已知后续工作

- **参数是帧制的，分享时要当心。** `kd` 是每帧系数而不是每秒，`loop_delay_frames` 更是
  直接以帧计。所以同一份调校在 241fps 和 120fps 的机器上效果不同。保持帧制是为了和
  回路本身一致（它就是逐帧驱动的），但这意味着调校 JSON 里除了 `measured_loop_ms`
  还应记录作者的帧率，导入时一并比对。
- **重置会清空在途历史，但物理上的指令还在路上。** 切换锁定目标时控制器会 `reset()`，
  `recent_commands` 被清空，而此前发出的指令接下来几帧才陆续落地。前馈拿不到它们的记录，
  会把我们自己的落地位移当成目标在动，产生一次虚假的提前量。切目标时误差本身也在突跳、
  污染更大，所以这不一定是主要矛盾——需要实际打过才知道值不值得修（可行的修法是让
  `reset()` 保留历史只清算法状态）。
- **控制质量的自动测量**：超调、稳定时间、跟踪误差。有了这些才能把手感判断换成数据判断。
- **算法参数的热更新**：目前只有 kp 能热更新，算法参数需重启。
- **`loop_delay_frames` 是机器属性却存在算法参数里**：两个方案各存一份，改了要改两处。
  这是通用 `PARAMS` 设计的代价——框架不认识任何具体参数名，插件才能自由声明。
  权衡后接受：若提升为全局配置，插件就得依赖框架预定义的字段名，扩展性受损。
- **`loop_delay_frames` 的默认值**：目前是 8（来自实测的 7~8 帧）。
  理想情况下应由程序自己测出来填进去，而不是让用户手填。

## 附录：拟人化运动的三个算法（2026-09-12）

现有算法都是「误差 × 动态 kp」的指数衰减接近：路径笔直，越近越慢。观感机械。
新增三个算法解决这一点，全部走和用户自写算法完全相同的契约，放在
`rhodes_fast/aim_algorithms/human.py`。

调研了两个主流做法（都来自浏览器自动化，不是瞄准领域）：
[ghost-cursor](https://github.com/Xetera/ghost-cursor)（1.6k star，三次贝塞尔，
控制点取直线**同一侧**，`path()` 在移动开始前算完整条轨迹）和
[WindMouse](https://ben.land/post/2021/04/25/windmouse-human-mouse-movement/)
（质点受恒定重力 + 平滑随机风，**每步增量更新**）。

**核心矛盾**：那些项目的场景是静止按钮、A 到 B、移完结束，预规划路径完全合理。
我们的目标 482px/s 在动且永不结束，预规划有两个致命问题——开环（提交 N 帧就是
N 帧不看画面，正是本项目一直在打的死区延迟），以及规划时的终点本来就是 7 帧前的
位置。所以三个实现**全部是增量式的**。

### 计算开销不是问题（实测）

| | compute() | 占一帧（241fps = 4,150,000 ns） |
|---|---|---|
| `p` | 416 ns | 0.010% |
| `feedforward` | 1208 ns | 0.029% |
| `inflight_ff` | 2832 ns | 0.068% |
| `feedforward_wind` | 4769 ns | 0.115% |
| `windmouse` | 4345 ns | 0.105% |

新算法约是 `feedforward` 的 4 倍（主要是 `random` 的调用开销），但仍只占一帧的
0.1%，相当于单次推理（1.79 ms）的 0.27%。**真正的代价是路径变长和横向偏离，
不是计算。**

### 拟人化的代价（1.5x 增益，拉枪 + 随机左右跟随，64 种子）

| 配置 | 抓到 ms | 回摆 px | 跟随均值 | ≤10px | ≤5px |
|---|---|---|---|---|---|
| `feedforward`（基线） | 35 | 38.6 | 10.4 | 54% | 37% |
| 风 0.0（护栏验证） | 35 | 38.6 | 10.4 | 54% | 37% |
| **风 0.35（默认）** | **119** | **18.3** | **10.7** | **56%** | **36%** |
| 风 0.7 | 148 | 20.9 | 11.3 | 51% | 33% |
| 贝塞尔 0.25 闭环 | 171 | 23.3 | 14.1 | 41% | 16% |
| 贝塞尔 0.6 闭环 | 304 | 39.1 | 27.6 | 14% | 4% |
| 贝塞尔 承诺 4 帧 | 290 | 27.6 | 19.4 | 26% | 8% |
| 贝塞尔 承诺 8 帧 | 34 | **78.1** | 23.4 | 25% | 9% |
| WindMouse 无风 | 97 | 16.0 | 12.0 | 45% | 28% |
| WindMouse 默认 | 98 | 16.0 | 12.9 | 42% | 25% |

四条结论：

- **风几乎免费**：在靶率与基线持平（56%/36% vs 54%/37%）。代价在别处——**首次咬上
  目标慢了 3.4 倍**（35 → 119 ms），因为弧线比直线长。跟踪阶段完全不受影响，这正是
  「近了归零」要保证的。
- **意外的副作用：风把回摆从 38.6px 降到 18.3px。** 因为横向偏离让你不是直冲目标，
  沿轴的过冲反而变小了。
- **贝塞尔在同名参数下比风贵得多**：`arc_strength=0.25` 的横向量是
  `3t(1-t)·0.25·dist`，t=kp≈0.12 时约 0.079·dist，即 100px 处每帧偏 7.9px 而前进
  12px——约 33° 的偏角，远大于风的默认值。两者的参数刻度不可直接比较。
- **承诺帧数的代价被量化了**：闭环 41%/16% → 承诺 4 帧 26%/8%，承诺 8 帧回摆爆到
  78px（盲走一条过期的路径）。这就是 `commit_frames` 这个旋钮存在的意义。

### 三处对 WindMouse 原版的改动

原版默认值（G_0=9, W_0=3, M_0=15, D_0=12）在 241fps 下**完全不可用**（实测跟随均值
79px、在靶率 0%）：它的单位是「每步」而假定步频远低于 241fps。标定后为
`gravity=4, wind=2, max_step=3, damp_px=25, lead_frames=8`。

`max_step` 是主导参数，其合理量级有个直白来源：241fps × 3px/帧 = 723px/s，与目标
自身横移速度（实测 482px/s）同量级；原版的 15px/帧 相当于 3600px/s。

**一个值得记住的发现**：`gravity` 在 4 附近就到平台（2.0 → 44%，32.0 → 45%）。
gravity 越大，速度越快饱和到上限，也就是**惯性越不起作用**。换句话说在有死区延迟的
闭环里，WindMouse 的动量项是负担，最好的配置恰恰是让它几乎不起作用的那个。

另外两处改动都源于「原版假设一次移动、到了就结束」而我们连续运行：速度上限改成按
距离算（原版把 M_0 永久调小，我们跑不完会把自己冻住）；去掉末端 3px 下限（那是为了
让离散循环终止，留着会在 ±3px 永久振荡）。还去掉了速度截断里的随机——241fps 下逐帧
速度抖动快到读不出人味（人的速度起伏在 100ms 即 24 帧的尺度上），而风本身时间相关，
那份可读的起伏已由它提供；去掉后 `wind` 成为唯一随机来源，`wind=0` 的轨迹完全确定，
风的贡献才能被隔离出来。

### 贝塞尔的一个漂亮性质

控制点沿轴取在 `aim/3` 和 `aim·2/3` 时：

```
3(1-t)²t·(1/3) + 3(1-t)t²·(2/3) + t³ = t[(1-t)+t]² = t
```

即 `B(t)` 代数上**恒等于** `t·aim`。所以这条弧线是纯横向叠加——沿轴的速度曲线和
`feedforward` 一模一样，加的只是弯，不是快慢。横向分量同理收成 `3t(1-t)·offset`，
在 t∈[0,1] 上恒不换号，弧线只往一侧鼓、绝不穿到另一侧（ghost-cursor 强调的
「控制点只取一侧」，两侧随机取会出扭曲的 S 形）。

### 变异测试逼出来的两处修正

- **「近了归零」原本有两套机制**（`distance >= wind_scale` 的注入闸门 + `growth`
  衰减），闸门干掉了绝大部分活（闸门一关，风 15 帧就衰减到千分之一），导致 `growth`
  的效果量不出来——删掉它测试照过。去掉闸门只留衰减项：一个机制、平滑淡出、
  `wind_decay_px` 成为唯一有意义的旋钮。
- **「和 feedforward 逐位相同」走的是提前返回那条捷径**，根本没经过曲线代码。而那个
  提前返回其实只是优化（`offset` 为 0 时 `aim*t - 0.0` 在 IEEE754 下就是 `aim*t`）。
  补了一条直接钉住上述恒等式的测试，和一条走 `commit_frames > 0` 路径验证退化的。

## 附录：实测结论（2026-09-12，以此为准）

实机试过之后，最好用的是 **`feedforward`（速度前馈）**，而 **`inflight`（扣在途）跟不上人**。
实测优先于下面的仿真表——仿真的被控对象一侧是模型假设，这里是真机。

仿真表和实测在「扣在途让跟踪变差」这一点上是一致的（29.4px vs 基准 21.7px）。
仿真排错的是**权重**：它拿 100px 定点拉枪的超调和跟踪各算一半分，于是 `inflight_ff` 综合最高。
但真实对手一直在横向拉扯，几乎没有「站定后收敛」这个阶段——跟踪那一项才是全部，
超调那一项赚的分在实战里根本兑不出来。而 `inflight` 恰恰是拿跟踪去换超调：
它假设目标不动，扣掉在途位移后控制器以为「已经发够了」，目标却在这段死区时间里又跑远了。

推论：`inflight_ff` 里真正干活的是前馈那一半，扣在途那一半是净负担。
它还要求 kp_max 提到 0.35（基准 0.143 的 2.4 倍），顺带把检测噪声也放大 2.4 倍。

## 附录：拉枪 + 随机左右跟随仿真（2026-09-12）

第一版仿真只测「对定点靶拉枪」和「对匀速目标跟踪」两个孤立场景，这一版把它们合成
实战场景：先 100px 拉枪，随后目标以 482px/s 每 80~350ms **随机换向**（模拟 A/D 拉扯）。
控制律直接驱动真实的 `KmboxController.move_toward`，所以死区、EMA、亚像素累加、限幅、
动态 kp、以及「进死区就清在途窗口」都在回路里；仿真只负责被控对象一侧。
其余条件：241fps、真实延迟 7±1 帧、检测噪声 σ=0.8px、64 个随机种子平均。

1.0x 增益 = `settings.txt` 方案 1 的实际值（kp_min/max/growth = 0.023/0.083/0.031）。

| 算法（1.5x 增益） | 抓到 ms | 回摆 px | 跟随均值 | 跟随 p95 | ≤10px | ≤5px |
|---|---|---|---|---|---|---|
| `p`（现状） | 33 | 43.2 | 17.9 | 25.2 | 14% | 7% |
| `pd` kd=0.6 | 49 | 19.2 | 14.1 | 20.5 | 27% | 11% |
| **`feedforward`** | 35 | 39.3 | **10.3** | 25.8 | **55%** | **38%** |
| `inflight` | 66 | 27.3 | 22.1 | 33.6 | 19% | 10% |
| `inflight_ff` | 66 | 17.0 | 15.7 | 20.4 | 15% | 7% |

**这一版与实测一致：前馈赢，而且赢得不小。** 换了场景就换了结论——说明第一版排错的
不是控制律，是场景。对随机换向的目标，`inflight_ff` 反而掉到接近 `p` 的水平，
印证了「它里面干活的是前馈那一半，扣在途那一半是净负担」。

### 前馈的增益工作点

| 增益 | 抓到 ms | 回摆 px | 跟随均值 | ≤10px | ≤5px |
|---|---|---|---|---|---|
| 1.0x（当前设置） | 54 | 23.1 | 15.8 | 14% | 7% |
| 1.2x | 44 | 28.6 | 12.6 | 51% | 7% |
| **1.4x ~ 1.6x** | 33~38 | 36~43 | **10.3** | 54~59% | **36~38%** |
| 2.0x | 26 | 58.0 | 11.9 | 50% | 26% |
| 2.5x | 48 | 61.4 | 16.1 | 37% | 18% |

**当前增益偏低。** 命中率的平台在 1.4~1.6x，代价是拉枪回摆从 23px 涨到 39px。
1.2x 那一行的错位（≤10px 已经 51%，≤5px 还是 7%）说明稳态偏移正好卡在 5~10px 之间。

### `loop_delay_frames` 的容差

1.5x 增益下 L=6~10 全部可用（≤10px 52~55%，L=8 最优），**L=11 直接崩**（9%）。
但 2.0x 增益下 L=10 就已经崩了。也就是说 **增益和 L 的容差互相挤占**：
增益越高，L 填错的惩罚越重。第一版规格里「L 填 8 而真实是 4」的警告方向是对的，
但悬崖实际在高估那一侧更陡。

`gain` 1.0 优于 0.8 和 1.2；`velocity_smoothing` 0.4 比 0.25 略好（均值 9.7 vs 10.3）。

### 这个仿真没建模的东西

目标是瞬时换向的（真人有加速过程，但 CS 式急停反而接近瞬时）；灵敏度按 1 鼠标单位
= 1 像素，真实值不是 1:1——不过这被增益倍数吸收了，所以「调到 1.5 倍」这个相对结论
可以迁移；检测框自身的宽高抖动没建模，只建了中心噪声。

## 附录：仿真数据

**注意：结论已被上面的实测推翻，此表仅作参数量级的参考。**

条件：延迟 7 帧抖动 1、检测噪声 σ=0.8px（从 83818 行真实日志的二阶差分测得）、
kp 按各方案单独调优。仿真的控制律部分已与真实 `KmboxController.move_toward` 对拍验证
（超调 37.0 vs 37.0、83.0 vs 83.0 完全一致），但被控对象一侧是模型假设，最终以实际手感为准。

| 算法 | 100px 拉枪超调 | 稳定时间 | 移动目标落后 482px/s |
|---|---|---|---|
| `p`（现状，kp=0.143） | 43.6 px | 180 ms | 21.7 px |
| `feedforward` | 43.6 px | 180 ms | 7.7 px |
| `inflight` | 0 px | 97 ms | 29.4 px（更差） |
| `inflight_ff`（kp=0.35） | 1.8 px | 73 ms | 10.1 px |
| `pd`（kd=0.6） | 12.8 px | 166 ms | 21.7 px（无变化） |

两条值得记下的结论：

- **`inflight` 单独使用会让跟踪变差。** 它假设目标不动；目标在动时在途位移补不上那段距离。
  实测证实了这一条，并且比仿真预测的更严重：对移动的人，配上前馈也救不回来。
- **`pd` 对移动目标落后零作用。** 匀速目标稳态下 `d(误差)/dt = 0`，微分项不输出。
  它治的是超调，而降 kp 治得更好也更快（kp=0.07 时超调 3.0px、稳定 86ms）。
  `pd` 仍然保留在内置清单里，因为亲手试一遍比看结论更有说服力。
