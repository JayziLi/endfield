# 预览里的瞄准轨迹

## 目的

在「实时预览」上直接画出准心扫过的路径，用来直观比较不同算法（弧线、上下晃、冲过头、
落后）。要的是**实战里真实的轨迹**：程序发的移动和手的移动都算进去。

参照 Aim Lab 回放的三条线：落后路径（已经走过）、领先路径（将要走）、最优路径（到目标的直线）。

## 看到什么

- **两个勾选框**：「画面」和「轨迹」，打开程序时只勾「画面」。
  - 只勾画面：推流画面，和以前一样。
  - 画面 + 轨迹：推流画面上叠加轨迹（含目标瞄准点轨迹）。
  - 只勾轨迹：黑底上只画准心轨迹（含在途虚线、勾了的话含最优路径），不画画面、识别框、FOV 圈、
    准心十字、底部状态栏和目标轨迹。主循环也不再为预览做全类别检测。
  - 都不勾：不渲染，页面提示「勾选「画面」或「轨迹」后在这里显示」。
  - 没勾轨迹时，「最优路径」和长度滑条是灰的。
- **准心轨迹**：最近 N 秒（滑条 0.2～2 秒，默认 0.5 秒）。终点在画面中心。
- **在途虚线**：从中心接着画「已经发出、还没出现在画面上」的那几帧移动，终点是准心此刻的真实位置。
- **颜色**：统一从黄（最新）渐变到灰（最旧），16 档；不分方案、不分是不是手在动。始终 2 像素宽。
  （第一版按方案分黄/青、手动灰白，且越旧越细；用户看过实物后改成统一黄→灰。）
- **目标瞄准点轨迹**：更暗的灰、1 像素细线，和淡成灰的准心轨迹靠粗细区分。换目标或丢目标处断开。
- **最优路径**（勾选，默认关）：点线，从这次瞄准的起点（触发键按下、或跟随中换了目标的那一帧）
  的准心位置，连到目标当前的瞄准点。起点移出轨迹窗口后不画。
- **状态文字**：画在预览画面左上角（底部状态栏在 320 宽的画面上已经写满），用 OpenCV 的英文字体：
  `trail calibrating` / `trail 0.63px/ct 7f` / `trail needs KMBox`。第一次标定成功时往运行日志打一行中文。
- **控件**：「实时预览」页顶部一排：画面、轨迹、最优路径、轨迹长度滑条。改动立即生效。

只有轨迹长度存进 `settings.txt` 的 `[ui]`（`trail_seconds`）；勾选框不存，每次打开都只勾画面。
上一版存过 `trail_enabled`、`trail_optimal_path`，读到就丢弃。都**不进预设**：看的偏好不是游戏配置。

## 数据怎么走

```
主循环(241fps) ──每帧写一行──> TrailRecorder(环形缓冲 4096 行 ≈ 17 秒)
                                     │ 只读已写完的行
预览线程(≤30fps) ──每秒最多一次──> 标定 ──> 算坐标 ──> 画进画面 ──> JPEG ──> GUI
```

每行：程序指令 dx/dy、手的位移 dx/dy、目标误差 x/y、目标编号（0=没目标）、当前方案（-1=没按触发键）。

- **主循环只写**：预分配的 numpy 数组，每帧一次整行赋值，写完再把行计数加一。不拷贝、不加锁。
- **读的一侧**：只读计数之前的行；复制完再看一眼计数，写入端下一个要覆盖的那一格（最旧一行）一律不给。
- **设置文件**：GUI 写 `.cache/gui-<pid>.trail.json`（先写临时文件再替换）。预览线程每 0.25 秒直接重读，
  不比修改时间：Windows 上修改时间精度可能只有十几毫秒，拖滑条时最后一次改动会读不到。
- **严格对齐**：每个预览任务带着自己那一帧的行号，轨迹画到那一行为止，不画到最新一行。
- **手的位移**：KMBox 监听线程本来就在跑（读触发键）。给它挂回调，把每个报文的 x/y 累加起来；
  主循环每帧取走并清零。库本身只保留最新一包，不累加。
- **没开 KMBox**：不画轨迹，状态栏写 `trail needs KMBox`。

## 标定

轨迹要两个数：**每计数像素**（取决于游戏灵敏度和采集缩放）和**回路延迟帧数** L。
运行时从环形缓冲里自动估，每秒最多一次，放在预览线程里做，每 512 帧 `sleep(0)` 让出一次 GIL。

1. **监听口含不含程序移动**：物理上只有含或不含。直接看程序发出一条指令（≥3 计数）后，
   接下来 4 帧的监听数据里有没有同样的位移，回归系数 ≥0.5 就是含。这一步不看画面，
   不受目标移动影响。含的话镜头移动 = 手，否则 = 程序 + 手。
2. 响应 `r[k] = e[k] - e[k-1]`，只取相邻两帧都有目标、而且是同一个目标的帧。
3. 延迟：`L = 1..30` 中，使「第 k-L 帧的镜头移动」与 `-r[k]` 相关系数最大的那个。
   按轴分别算、合在一起统计。只用移动量 ≥6 计数的帧，配对不足 200 再放宽到 3、1。
4. 比例：这个 L 上的回归斜率 `Σxy / Σxx`。
5. **跨次累加**：每次只处理没见过的新行，求和统计量按处理的帧数衰减（每 241 帧 ×0.99，
   记忆约 100 秒）。换 lag 要比当前 lag 的相关系数高 0.03 以上（滞回）。
6. 接受条件：相关系数 ≥0.25、比例 >0。不满足就显示「标定中」。

为什么这样定（数据都在 `trail.py` 注释里）：
- 门槛 3 时跟随偏差严重（仿真 0.39，真值 0.63）：跟随时准心和目标同向运动。门槛 6 只剩
  拉枪帧，20 个种子不跟随时无偏（0.636），强跟随仍偏低约 15%（0.53）。9/9 真实日志在门槛
  3/6/12 下是 0.636/0.656/0.616，实战偏差小得多。
- 差分可以消掉目标速度、无偏，但标准差 0.2～6，不能用。多抽头回归在门槛 6 下和单帧一样。
- 不累加时，17 秒一段的真实日志比例在 0.38～1.08 之间跳。衰减 0.97 仍然 0.44～0.89、延迟换 46 次；
  0.99 + 滞回：每秒变化 p95 2%，延迟一整局只换 1 次。
- 验证方法留给用户：拉枪打静止目标时，灰色目标轨迹应该收成一个点。

## 坐标

记 `m[i] = px_per_command·指令[i] + px_per_hand·手[i]`（像素），`C(i) = Σ m[0..i]`。
正在显示的是第 k 帧，中心为 `c`：

- 准心在「截止第 i 帧发出的移动都落地」时的位置：`P(i) = c + (C(i) - C(k-L))`。
  `i ≤ k-L` 是实线（已经在画面里），`k-L < i ≤ k` 是虚线（在途）。
  实线取 `i ∈ [k-L-T, k-L]`，T = 轨迹长度对应的帧数。
- 第 j 帧看到的目标瞄准点，换算到第 k 帧的画面上：`c + e[j] - (C(k-L) - C(j-L))`，`j ∈ [k-T, k]`。

## 性能要求与实测

| 项目 | 要求 | 实测 |
|---|---|---|
| 主循环每帧新增（记一行 + 取手的位移） | ≤5 微秒 | 1.8～3.1 微秒 |
| 监听回调每包 | — | 0.57 微秒 |
| 画 2 秒轨迹（483 点） | ≤2 毫秒 | 0.91 毫秒 |
| 标定增量（241 行） | ≤5 毫秒 | 1.09 毫秒 |
| 预览刚打开时补 4095 行 | — | 16 毫秒，分 8 块、块间让出 GIL |

实机验收留给用户：开关轨迹各录一段延迟日志，主循环每帧耗时平均和 p95 没有明显变化。

## 硬件自检工具

`kmbox-monitor-check.bat`（`tools/kmbox_monitor_check.py`）：
1. 手离开鼠标，程序发 10×100 计数再移回来，看监听口报回多少（含不含程序移动）。
2. 只按按键不动鼠标，看报文里会不会带着旧的位移。
3. 鼠标抵着书边来回推 20 次，看每次回到左端时累加值是否漂移（丢包）。

## 不做

- 慢放 / 回放 / 定格（Aim Lab 在回放里做，实时预览做不了；以后单独做）。
- 同场景仿真对比台。
- 数字抖动读数。
